# 技术笔记：桌面图标与任务栏的外部控制

> 这份笔记记录的是**实测结论**，不是理论推测。每条结论后面都附了数据或复现方法。
> 如果你也在做类似的事（桌面覆盖层、任务栏控制、图标特效），可以直接抄结论少走弯路；
> 更重要的是**那几个"看着可行、实测不行"的路线**，它们才是真正花时间的地方。

测试环境：Windows 11 25H2 (Build 26200.7840) · 2560×1440 · Wallpaper Engine 运行中 · 双显示器

---

## 一、隐藏/显示桌面图标

### 结论

| 项目 | 结论 |
|---|---|
| 官方开关 | 向 `SHELLDLL_DefView` 发 `WM_COMMAND, 0x7402` |
| 语义 | **取反**，不是"设为隐藏" |
| 持久状态 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Advanced\HideIcons` (DWORD) |
| 窗口定位 | `GetShellWindow()` → `SHELLDLL_DefView` → 递归找 `SysListView32` |

### 两个坑

**坑 1：不能依赖取反。**
`0x7402` 是取反语义，而**窗口可见性与 shell 内部状态会脱节**（比如上次异常退出）。
"读可见性再取反"会翻错方向 —— 实测 `--hide` 在这种情况下完全失效。

正确做法：
1. 以注册表 `HideIcons` 作为 shell 持久状态的基准，**只有它和目标不一致时才发 `0x7402`**
2. 视觉状态一律用**绝对操作**强制（`ShowWindow` + 分层不透明度），不依赖取反
3. 最后校验注册表，必要时显式写入

**坑 2：`ShowWindowAsync` 与 `ShowWindow` 的差别。**
跨进程调用同步的 `ShowWindow` 会**等待 explorer 完成**，第二次调用会被拖慢约 15ms。
需要连续操作（图标 + 任务栏同时出现）时用 `ShowWindowAsync`。

### 实测：图标重绘延迟约 270ms

`ShowWindow(SW_SHOW)` 之后，explorer 重新绘制 81 个图标需要 **约 270ms**。
用逐帧像素采样测出：画面在 293ms 处发生阶跃，之后不再变化。

这个延迟是本项目"图标与任务栏不同步"问题的根源，也是图标淡入方案必须解决的隐藏成本。

### 多显示器

每个显示器可能各有一套 `WorkerW + SHELLDLL_DefView + SysListView32`
（枚举 32 个顶层窗口时可同时发现多套）。
**只找一套会漏屏** —— 隐藏不干净，用户会看到另一块屏上的图标还在。

## 二、任务栏整条平移（最难的一步）

### 结论

| 尝试 | 结果 |
|---|---|
| 单纯 `SetWindowPos(Shell_TrayWnd, ...)` | ✗ **1ms 内被弹回原位** |
| `SetWindowPos` + **`SWP_NOSENDCHANGING`** | ✅ **位置稳定保持** |
| `ABM_SETAUTOHIDEBAR` | ✗ 无效 |
| `PostMessage(Shell_TrayWnd, WM_TIMER, 3, 0)` | ✗ 无效 |
| `SetWindowRgn` 裁剪 | ⚠️ 有效但只是"揭示"不是"平移"，用户不接受 |

### 原理

shell 在 `TrayUI::WndProc` 里拦截 `WM_WINDOWPOSCHANGING` 并把位置改回去。
`SWP_NOSENDCHANGING` 让这次 `SetWindowPos` **不发送该消息**，于是 shell 没有机会改回来。

> 这个突破口来自阅读 [Windhawk](https://windhawk.net/) 及其 mod 的源码，
> 其中能看到 `TrayUI::SlideWindow` / `TrayUI::_Hide` / `CSecondaryTray::_AutoHide` 等内部实现。

### 注意事项

- 必须记录任务栏的"正常位置"作为动画基准，且**只在底边贴合显示器下边缘时才记录**
  （否则任务栏在顶部/侧面时会算出错误的基准）
- 动画用 ease-out cubic，约 240ms，与图标淡入（250ms）自然同步

## 三、图标淡入：三次尝试，两次失败

这是整个项目最花时间的部分。目标：**让桌面图标从透明渐变到不透明，同时不改变壁纸的任何像素**。

### ✗ 尝试 1：给图标窗口加分层属性

```c
SetWindowLongPtr(lv, GWL_EXSTYLE, ex | WS_EX_LAYERED);
SetLayeredWindowAttributes(lv, 0, alpha, LWA_ALPHA);
```

**看起来很合理，实测不行。**

| 测量项 | 结果 |
|---|---|
| `alpha=0` 时画面 | **≈ 纯壁纸**（差异 3.31，噪声 0.78）—— 图标确实消失了 ✅ |
| `alpha=128` 时**空白区**颜色 | 基准 `DEEEE1` → `6F7870`（**正好变成一半亮度**）❌ |
| `alpha=255` 时与基准差异 | **170.83**（整片区域变黑）❌ |

**原因**：桌面 `SysListView32` 的合成表面在**未绘制区域是纯黑的**（不是透明的）。
不加颜色键时，整窗 alpha 会把黑色背景一起混合上去 → 壁纸被压黑。

**关键数据**：`DEEEE1 → 6F7870` 正好是 50%，这个数字直接证明了"未绘制区域是纯黑"。

### ✗ 尝试 1b：加颜色键救它

```c
SetLayeredWindowAttributes(lv, 0x000000, alpha, LWA_COLORKEY | LWA_ALPHA);
```

| 颜色键 | 与基准差异 |
|---|---|
| 无键 + alpha=128 | 93.54 |
| **`0x000000` + alpha=128** | **16.66** ✅ |
| `0x010101` + alpha=128 | 93.08 ❌ |
| `0xFFFFFF` + alpha=128 | 93.43 ❌ |
| `0x101010` + alpha=128 | 92.81 ❌ |

**颜色键确实把背景镂空了**（93.54 → 16.66），而且只有**精确的 `0x000000`** 有效 ——
这反过来精确证明了背景就是纯黑，不是近似黑。

**但是**：加了颜色键之后，**`LWA_ALPHA` 被忽略** ——

```
颜色键=0x000000 时依次设 alpha = 0 / 64 / 128 / 192 / 255
→ 图标淡化度全部为 0.0%（图标始终保持完全不透明）❌
```

**所以"背景镂空"和"整体淡入"两个效果无法同时拿到**。这条路走到头了。

### ✗ 尝试 2：抓一帧壁纸盖在图标上再渐隐

思路：截图 → 显示图标 → 用截图以 alpha=255 盖住 → 渐隐 → 露出真图标。

**对静态壁纸可行，对 Wallpaper Engine 不可行。**

现存方案（如 [Transparent Desktop Icons with Spotlight](https://windhawk.net/mods/transparent-desktop-icons-spotlight)）
正是这么做的 —— 它读取注册表里的**静态壁纸图片**重新渲染，所以和动态壁纸必然对不上。
社区 issue 也印证了这点：
[desktop-live-overlay · Overlay not visible with Wallpaper Engine](https://github.com/ramensoftware/windhawk-mods/issues/5440)
（该 issue 环境为 Windows 11 Build 26200 + Wallpaper Engine，与本项目测试环境一致）。

### ✗ 尝试 2b：抓屏相减求"图标蒙版"

思路：抓两张屏（有图标 / 无图标）相减，只有图标像素会变 → 得到精确蒙版。

**在动态壁纸下彻底不可用。**

```
350ms 间隔的两张纯壁纸截图：9.7% 的像素差值超过阈值（237286 px）
```

我之前用"区域平均差"（0.6~1.1）估算，误以为噪声很小；
**均值小不代表单像素小** —— 这是本项目最值得记住的教训之一。

### ✅ 尝试 3：自绘逐像素透明幕布

#### 关键发现

**桌面 ListView 的表面 = "图标叠在纯黑上"。**

用 `PrintWindow` 抓桌面 ListView 得到的图像，其全屏直方图实测为：

```
m=0    : 3,549,071   ← 96.6%，背景是【精确的 0】
m=1-2  :       217
m=3-5  :       192
m=6-15 :       688
m=16-45:     2,907
m=46+  :   133,325   ← 图标内容
```

**背景精确为 0** 这一点是整套方案的基础。

#### 实现

1. `PrintWindow` 抓桌面 ListView 到 32 位 DIB
2. 按亮度生成逐像素 alpha（`纯黑 → 全透明`，`亮度 ≥ 21 → 完全不透明`），保留反锯齿边缘的渐变
3. 用 `CreateWindowEx(WS_EX_TOPMOST | WS_EX_LAYERED | WS_EX_TRANSPARENT ...)` 建一块最顶层幕布
4. `UpdateLayeredWindow` + `AC_SRC_ALPHA` 上传，用 `BLENDFUNCTION.SourceConstantAlpha` 逐帧调透明度
5. 淡入的同时把真 ListView 显示出来在幕布背后重绘，重绘完（约 270ms）再撤幕布 —— 顺手把重绘延迟也藏掉了

#### 实测验证：对壁纸零覆盖

```
alpha=  0   与纯壁纸差= 2.87   与图标版差=26.34   壁纸样本变化=0.83
alpha= 64   与纯壁纸差= 7.11   与图标版差=21.44   壁纸样本变化=0.84
alpha=128   与纯壁纸差=12.02   与图标版差=16.50   壁纸样本变化=0.84
alpha=192   与纯壁纸差=17.04   与图标版差=11.86   壁纸样本变化=0.78
alpha=255   与纯壁纸差=21.57   与图标版差= 7.07   壁纸样本变化=0.69
（本次运行的动画噪声基准 = 1.12）
```

**壁纸样本变化在所有 alpha 下都等于噪声水平** —— 这说明幕布**物理上没有覆盖过壁纸的任何像素**，
不是"盖住了但看不出来"。这就是"对 Wallpaper Engine 零影响"的证据。

#### 两个必须避开的坑

**坑 A：不要试图"换背景色抓两张解方程"。**

理论上很漂亮：

```
背景填纯黑：c1 = C × α
背景填纯白：c2 = C × α + 255(1-α)
相减 → α = 255 - (c2-c1)，与图标颜色 C 无关，精确
```

**实测灾难**：`PrintWindow` 带 `PW_RENDERFULLCONTENT` 时用的是 **DWM 重定向表面快照**，
**连续调用两次会返回同一张缓存** → `c2 == c1` → 解出 `α = 255` → **整屏被不透明覆盖，桌面变黑**。

日志铁证：`cached 2537x1351 (opaque=3427487, semi=0)` —— 342 万像素全部"不透明"。

**坑 B：不要用"黑色 = 背景"做连通性填洞。**

想法：从图像四边泛洪，走不到的黑区 = 图标自己的黑底 → 判为不透明。

**实测结果**：`enclosed dark px = 310262` —— 图标之间的正常空隙也被当成"被围住的暗区"，
于是**到处都是黑方块**。

（这个方向在原理上是对的，但需要一个真正能区分"图标内部黑底"与"图标之间空隙"的判据，
单纯的四边泛洪做不到。）

## 四、其他实测细节

### 选中高亮框会被抓进素材

被选中的图标会被 shell 画一个**半透明高亮框**。
这个框在"黑底抓图"里变成深色像素，被亮度映射当成图标内容 → 淡入动画里出现黑方块。

**解决**：抓素材前用 `LVM_SETITEMSTATE`（`iItem = -1` 作用于全部项）**清掉选中状态**。
跨进程发送该消息需要把 `LVITEM` 结构放进目标进程的内存（`VirtualAllocEx` + `WriteProcessMemory`）——
**绝不能直接传本进程的指针**，那会让 explorer 读到非法地址。

清除时机选择在"图标本来就看不见"的时刻（预览开始 / 松手隐藏前 / 交接抓图前），用户完全察觉不到。

### 抓一次素材的真实成本

```
icon fade: cached 2525x1339 ... bitmap 13206 KB, took 94~125 ms
```

约 **100ms CPU**，瞬时内存约 30MB（用完立刻释放），**GPU 占用 0**（纯 GDI）。
空闲时完全没有开销。

### 保险丝

抓图退化时（例如上面那个"整屏不透明"的故障），会导致整块不透明内容盖住桌面。
所以加了一道判据：**不透明像素占比 > 50% 就放弃淡入**（正常值约 4~13%）。

**这道保险丝的价值**：让后续所有实验的最坏结果变成"没有动画"，而不是"把用户桌面弄坏"。

## 五、可复现的测量方法

本项目的所有结论都是用同一套方法测出来的，你也可以复用：

1. **基准采集**：图标可见时抓一帧、图标隐藏时抓一帧 → 得到"图标信号"
2. **噪声基准**：相隔 500ms 抓两帧纯壁纸 → 得到"动画噪声"（动态壁纸下约 0.6~1.1）
3. **判定标准**：任何测量值超过噪声 2~3 倍才算"有变化"，否则视为无影响
4. **逐帧采样**：用 `BitBlt` 抓屏 + 逐像素比对，间隔 25ms，可精确测出阶跃时刻
5. **直方图**：直接统计像素值分布，用来判断"背景到底是不是精确的 0"这类问题

工具都是一次性的控制台程序：建窗口、抓屏、比对、写 UTF-8 日志。
**建议每个假设都先写一个几百行的小探针验证，再动主程序** —— 这是本项目用两次"把桌面弄坏"换来的教训。

## 六、结论速查表

| 想做 | 该用什么 | 不该用什么 |
|---|---|---|
| 隐藏桌面图标 | `WM_COMMAND 0x7402` + 绝对 `ShowWindow` | 依赖取反语义 |
| 移动任务栏 | `SetWindowPos` + **`SWP_NOSENDCHANGING`** | 不带该标志（会被 1ms 弹回） |
| 让图标淡入 | **逐像素透明最顶层幕布** | 给图标窗口设整窗 alpha；抓静态壁纸；抓屏相减 |
| 让背景镂空 | 精确颜色键 `0x000000` | 近似色（`0x010101` 无效） |
| 覆盖桌面但不影响壁纸 | 只在不属于背景的像素上不透明 | 整块覆盖（必然覆盖壁纸） |
| 判断抓图是否退化 | 不透明像素占比 | —— |
| 测"有没有影响" | 对比噪声基准 | 看区域平均差（会掩盖单像素剧变） |
